# PowCoin (PWC) — 작업증명(PoW) 암호화폐 레퍼런스 구현

> ⚠️ **현재 상태: 단일 노드 레퍼런스 구현**이다. 합의 규칙·서명·이중 지불·승수 로직은
> 테스트로 검증했지만 P2P 네트워크, 포크 선택, 영속 저장소, 보안 감사가 없으므로
> 이 상태로 거래소에 상장하거나 실제 자산을 다뤄서는 안 된다. 아래 "실제 출시 전 필요 작업" 참고.

## 파일 구조

```
pow-coin/
├── README.md
├── requirements.txt          # cryptography, pytest
├── demo.py                   # 데모 시나리오
├── powcoin/
│   ├── __init__.py
│   ├── hashing.py            # 정규 JSON 직렬화, SHA-256, 앞자리 0비트 판정
│   ├── wallet.py             # ECDSA(secp256k1) 키쌍, 서명/검증, 주소
│   ├── transaction.py        # 거래, 서명, coinbase, 단위(1 PWC = 10^8)
│   ├── block.py              # 블록(index, timestamp, transactions, prev_hash, miner, difficulty, nonce, hash)
│   └── blockchain.py         # 합의 규칙, 채굴, 체인 검증, 난이도 조정, 보상, 승수, 저장/로드
└── tests/
    └── test_powcoin.py       # 27개 테스트
```

## 핵심 규칙

| 항목 | 구현 |
|---|---|
| 채굴 성공 조건 | `SHA-256(블록 데이터 + str(nonce))`의 앞 N비트가 0 (시작 N=15, 확률 1/2^15) |
| 난수 | 채굴·승자 결정에 `random` 미사용. nonce를 0부터 1씩 증가 → 누구나 재현·검증 |
| 난이도 조정 | 10블록마다 직전 구간 평균 블록 시간이 목표의 1/2 미만이면 +1비트, 2배 초과면 −1비트 |
| 보상 | 50 PWC, `halving_interval`(기본 210,000) 블록마다 반감, 총 발행량 21,000,000 PWC 상한 |
| coinbase | 블록 첫 거래, 수령자 = `block.miner`, 금액 = 보상 + 수수료 (정확히 일치해야 함) |
| 이중 지불 | 잔액 부족 거부, 같은 tx_id 거부, 계정별 nonce 순번 강제 (대기 중 거래까지 합산) |
| 승수(wins) | 검증 통과 블록이 추가될 때만 +1. `recount_wins()`로 체인 `miner` 필드에서 언제든 재계산 가능, 로드 시 재검증 후 재계산 |

## 실행 방법

```bash
cd pow-coin
pip install -r requirements.txt
python demo.py
python -m pytest -q
```

## 실제 출시 전 필요 작업

1. **P2P 네트워크와 합의**: 노드 간 블록/거래 전파, 최장(누적 작업량 최대) 체인 선택, 재조직(reorg) 처리.
2. **보안 난이도**: 15~16비트는 노트북으로 1초 안에 수십 블록을 다시 채굴할 수 있어 51% 공격이 사실상 무료다.
   초기 해시파워가 작은 신규 PoW 코인은 기존 채굴풀에 의한 공격 위험이 매우 크다(병합채굴, 체크포인트 등 검토).
3. **난이도 알고리즘**: ±1비트(2배 단위) 조정은 거칠다. 목표값(target) 기반의 연속적 조정과 타임스탬프 조작 방어
   (median-time-past) 필요.
4. **저장소/성능**: JSON 전체 재검증 대신 DB(LevelDB/RocksDB), UTXO 또는 상태 트리, 블록 크기 제한.
5. **서명**: secp256k1 low-S 정규화, 체인 ID를 서명에 포함(다른 체인에서의 재전송 방지).
6. **외부 보안 감사, 테스트넷 장기 운영, 버그 바운티.**
7. **법·규제**: 국내 거래소 상장은 DAXA 공동 상장심사 기준, 「가상자산이용자보호법」, 특금법(자금세탁방지),
   백서·공시·유통량 계획이 필요하다. 반드시 법률 자문을 받을 것.

## ERC-20 스마트 컨트랙트로 옮길 때 고려할 점

- **PoW가 필요 없어진다**: 이더리움 자체가 합의를 담당하므로 블록/해시 연결/난이도 조정/체인 검증 코드는 사라지고
  `balanceOf`, `transfer`, `approve`, `transferFrom`, `totalSupply`, `Transfer`/`Approval` 이벤트로 축소된다.
- **서명·이중 지불·nonce**: 이더리움 계정의 서명과 nonce가 대신 처리한다. 오프체인 서명 전송이 필요하면 EIP-2612 `permit`.
- **"채굴 보상"을 유지하려면**: 컨트랙트 안에서 `keccak256(challenge, msg.sender, nonce) < target`을 검증하는
  "mineable token"(예: 0xBitcoin, EIP-918) 형태가 된다. `msg.sender`를 해시에 넣어 남의 해답 가로채기(front-running)를
  막아야 하고, 해답 1회 사용 후 challenge를 갱신해야 한다. 블록 수 대신 `block.timestamp`/민팅 횟수로 반감·난이도를 계산.
- **발행 상한**: `totalSupply + reward <= MAX_SUPPLY`를 `_mint` 전에 강제. 소수점은 `decimals = 8`로 현재 단위와 맞출 수 있다.
- **승수**: `mapping(address => uint256) public wins;`를 민팅 성공 시에만 증가시키고 `Mined(miner, wins)` 이벤트를 발생시킨다.
  리더보드 정렬은 가스 비용 때문에 온체인에서 하지 말고 이벤트를 인덱싱(The Graph 등)해서 오프체인에서 만든다.
- **가스/보안**: 해시 검증은 저렴하지만 루프·정렬은 피한다. OpenZeppelin ERC-20 상속, 소유자 권한 최소화(또는 포기),
  업그레이드 가능 여부 결정, 외부 감사 필수.
- **정수 연산**: Solidity 0.8+는 오버플로를 자동 검사한다. 반감은 `>>` 시프트로 동일하게 구현 가능.
